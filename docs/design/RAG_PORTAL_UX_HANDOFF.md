# RAG Portal 디자인·UX 핸드오프

> 버전 1.0 · 대상: RAG를 처음 만드는 한국어권 비전문가 · 구현 기준: React + TypeScript + styled-components

## 1. 디자인 방향

RAG Portal은 “AI가 답을 잘해 보이는 화면”이 아니라 **문서에 근거해 답을 확인하고, 내 문서에 맞는 검색 방식을 고를 수 있는 작업 공간**이다. NotebookLM의 넉넉한 여백, 소스 중심의 작업 흐름, 클릭 가능한 인용 패턴에서 영감을 받되, 브랜드·레이아웃을 복제하지 않는다.

핵심 원칙은 세 가지다.

1. **쉬운 말이 먼저, 원리는 필요할 때.** 기본 라벨은 `일반 검색`, `정밀 검색`, `정확히 찾기`처럼 쓴다. 기술 용어는 `?` 도움말에 `하이브리드(BM25+벡터)`처럼 병기한다.
2. **답변과 근거는 분리하지 않는다.** 답변 문장 안 인용 칩을 누르면 해당 문서·원문 조각을 즉시 연다. 근거가 약하면 그 사실을 답보다 먼저 보인다.
3. **진행 중에도 사용자는 자유롭다.** 처리 상태는 페이지를 막는 모달이 아니라 대시보드와 상세 화면에서 계속 확인한다. 현재 단계, 완료 수, 재시도 이유를 명확히 보여준다.

권장 톤은 차분하고 정확하며 격려적이다. 실패·미완료를 사용자의 잘못처럼 말하지 않는다. 예: `문서를 준비하고 있어요. 완료되면 비교를 시작할 수 있어요.`

## 2. 시각 기반

프론트엔드는 [rag-portal-tokens.css](../../assets/design/rag-portal-tokens.css)를 전역으로 한 번 불러온 뒤, 같은 값을 styled-components 테마로 매핑한다. 업무 페이지에서 원시 색상값을 직접 쓰지 않는다.

| 요소 | 기준 |
|---|---|
| 배경 | 약간 따뜻한 오프화이트 `--rp-canvas`; 콘텐츠 표면은 흰색 |
| 기본 글자 | `--rp-ink`, 본문 14–16px, 줄간격 1.55 |
| 강조 | 차분한 파랑 `--rp-action`; 보라색은 보조 강조에만 사용 |
| 카드 | 14px radius, 얇은 border, 매우 약한 그림자. 카드 안에 또 카드가 필요하면 안쪽은 border만 사용 |
| 여백 | 페이지 32–48px, 섹션 32px, 카드 20–24px, 관련 요소 8–12px |
| 밀도 | 답변과 문서에는 넉넉하게, 상태·메타데이터에는 압축해서. 같은 시각적 무게의 CTA는 한 영역에 하나만 둔다 |
| 아이콘 | 텍스트를 대체하지 않는다. 상태 배지에는 아이콘+텍스트를 함께 표기 |

### 타이포그래피

- 한국어 시스템 폰트 우선순위는 토큰의 `--rp-font-sans`를 따른다. 초기 버전에서 외부 웹폰트는 필수가 아니다.
- 페이지 제목 30px/700, 화면 내 제목 24px/700, 섹션 제목 20px/600, 카드 제목 16px/600, 본문 14–16px/400을 사용한다.
- 숫자·파일명·기술 식별자는 필요 시 `--rp-font-mono`를 부분 적용한다. 긴 ID를 카드의 주요 정보처럼 보이게 하지 않는다.

### 상태 의미

| 의미 | 토큰 | 필수 보조 표현 |
|---|---|---|
| 준비 완료·확정 | success | 체크 아이콘 + `준비 완료`/`확정됨` |
| 처리·스트리밍 | progress | 진행 아이콘 + 현재 단계 또는 `2/3 완료` |
| 검토 필요·지연 | warning | 안내 아이콘 + 원인/다음 행동 |
| 실패·근거 부족 | danger | 오류 아이콘 + 재시도/다른 행동 |
| 설정 전·읽기 전용 | neutral | 상태 텍스트 |

색상만으로 처리 상태, 선택, 오류, 인용의 의미를 전달하지 않는다.

## 3. 공통 컴포넌트 명세

아래 컴포넌트는 `src/shared/ui/rag/`처럼 한 위치에 만들고, `Hana*` 어댑터가 있다면 그 위에 얇게 조합한다. 화면별 CSS 복제는 금지한다.

| 컴포넌트 | Props/상태 | UX 규칙 |
|---|---|---|
| `RagStatusBadge` | `settingUp | parsing | chunking | indexing | ready | failed`, optional progress | 아이콘·텍스트·진행수를 함께 표시. `임베딩 중 2/3`처럼 단일 문장으로 읽힌다. |
| `RagStepProgress` | steps, activeStep, completedCount | 대기/진행/완료/실패 단계가 모두 구분된다. 단순 spinner로 대체하지 않는다. |
| `DocumentScopeList` | documents, selectedIds, onChange | 체크박스와 파일명, 확정 조합 요약을 한 행에 표시. 행 전체 클릭과 체크박스 클릭이 중복 토글되지 않게 한다. |
| `AnswerComposer` | value, onSubmit, disabled, streaming | 입력에는 예시 질문 placeholder를 제공. 스트리밍 중 `중단`은 별도의 명시적 위험도 낮은 버튼으로 둔다. |
| `AnswerMessage` | answer, citations, elapsed, feedback | 답변 문장 내 `CitationChip`을 렌더링. 근거 부족 응답은 경고 표면·명확한 문구를 사용하고 출처를 꾸며내지 않는다. |
| `CitationChip` | source title, excerpt, targetId | 호버/포커스에 미리보기, Enter/Space에 원문 조각 열기. tooltip만으로 핵심 정보를 숨기지 않는다. |
| `EvidencePanel` | source, segment, highlightedRanges, open | 인용을 누르면 사이드 패널 또는 페이지 내 패널이 열리고 해당 원문을 스크롤·강조한다. 닫은 뒤에는 원래 트리거로 포커스를 돌린다. |
| `PipelineCandidateCard` | candidate, answer status, selected, voteCount | 카드 전체를 checkbox label로 만들지 말고, 독립 체크박스와 명확한 제목을 둔다. 답변/근거/시간/원본보기 순서를 고정한다. |
| `SearchModeSelect` | options, selected, help | 문서 조합이 서로 다를 때만 나타난다. 기술 용어는 도움말에만 사용한다. |
| `SensitivityControl` | flexible/standard/strict | 세그먼트 버튼 또는 radio group. 기본은 `평이하게`; 튜닝 모드에서는 렌더링하지 않는다. |
| `AsyncStatePanel` | loading/empty/error/forbidden/partial | 모든 페이지에서 동일한 구조: 현재 상태, 이유, 다음 행동. |
| `ConfirmFinalizationDialog` | winner, lastQuestion, lastAnswer | 확정 대상과 임시 결과 정리의 영향을 보여준다. 기본 포커스는 `다시 비교하기`에 둔다. |

### 버튼 계층

- Primary: 한 영역에서 가장 중요한 다음 행동 하나만. 예: `새 RAG 만들기`, `확정하기`.
- Secondary: `다음 라운드 진행`, `문서 추가`.
- Tertiary/text: `원본 조각만 보기`, `다시 비교하기`, `도움말`.
- Destructive: 문서 삭제·임시 결과 폐기. 삭제 대상 이름, 되돌릴 수 없음 여부를 확인 화면에 포함한다.
- 비활성 완료 버튼에는 반드시 이유를 인접 텍스트로 둔다. 예: `동점인 조합이 있어 한 가지를 더 선택해 주세요.`

## 4. 정보 구조와 핵심 사용자 여정

### 4.1 RAG 대시보드: 10초 스캔

목적은 사용자가 “무엇이 준비됐고, 어디로 돌아가야 하는지”를 한눈에 확인하게 하는 것이다.

```text
페이지 헤더: RAG 대시보드                         [ + 새 RAG 만들기 ]
요약: 준비 완료 3 · 설정 중 1 · 확인 필요 1

[RAG 카드] [RAG 카드] [RAG 카드]
이름       이름       이름
● 준비 완료 ◐ 임베딩 중 2/3  ! 재튜닝 권장
문서 3 · BGE-M3  문서 1 · BGE-M3  문서 4 · BGE-M3
최근 작업 시각 / 재개 또는 열기
```

- 1440px 이상은 3열, 1024–1439px는 2열, 그 아래는 1열이다. 카드 높이는 내용에 따라 늘어나되 한 행 안에서 불필요하게 고정하지 않는다.
- 처리 중 카드는 CTA를 `진행 상황 보기`로, 설정 중은 `이어서 설정하기`로 바꾼다.
- 재튜닝 권장에는 부정 피드백 수 같은 내부 원점수를 전면 노출하지 않는다. `최근 답변에 대한 확인이 더 필요해요`와 `상세 보기`를 제공한다.

### 4.2 생성: 질문 → 업로드 → 자동 처리

1. **간단한 설정 질문**: 한 화면에 한 질문. 진행률 `1/3`과 이전 버튼 제공. 추천 결과에는 `추천 이유`를 펼쳐 볼 수 있게 한다. 모델을 고른 즉시 인스턴스는 `설정 중`으로 생성된다.
2. **업로드**: 모델 요약을 작게 고정하고, 중앙에 단일 dropzone을 둔다. 지원 형식/제한/개인정보 유의 사항을 dropzone 아래에 짧게 쓴다. 업로드 완료가 파싱 완료를 뜻하는 것처럼 보이게 하지 않는다.
3. **처리**: 업로드 즉시 비차단 상태로 전환한다. `파싱 중 → 후보 찾는 중 → 비교를 준비하는 중`을 보여주며, 사용자는 대시보드로 돌아갈 수 있다. 후보가 먼저 준비되면 비교 화면에 자동 합류시킨다.
4. **비교**: 한 질문에 대해 준비된 후보들의 답을 같은 조건으로 비교하고, 1개 이상 선택한다. 비전문가에게 점수·임계값을 요구하지 않는다.
5. **확정**: 단독 1위가 있을 때만 완료 CTA를 활성화한다. 확인 후에만 임시 후보를 정리한다.

### 4.3 비교 화면: 튜닝 모드임을 분명하게

```text
상단: [튜닝 중]  라운드 2 · 문서: 출장비_지급_규정.pdf
      “답변과 근거를 비교해 가장 도움이 되는 결과를 하나 이상 골라 주세요.”

질문 입력 ------------------------------------------------- [비교하기]

[ □ 조항 단위 · 일반 검색     선택 1회 ]   [ □ 문단 단위 · 정밀 검색  선택 0회 ]
  답변 (독립 SSE 스트리밍)                   답변
  문장 안 [1] [2] 인용                        문장 안 [1] 인용
  [원본 조각만 보기] · 응답 1.8초              [원본 조각만 보기] · 생성 중…

하단 고정 action bar: 도움말 | [다음 라운드 진행] [완료(조항 단위·일반 검색)]
```

- 6–9개 후보는 CSS Grid `repeat(auto-fit, minmax(18rem, 1fr))`을 사용한다. 데스크톱은 3–4열, 1024px 이하에서는 2열이다. 좁은 화면에서 카드 안 가로 스크롤은 허용하지 않는다.
- 스트리밍 카드에는 skeleton 2–3줄과 `답변을 만드는 중…`을 보여 주고, 먼저 완성된 카드의 선택·근거 기능은 즉시 사용 가능하게 한다.
- 후보 이름은 쉬운 표현 + 청킹 단위(`조항 단위`, `문단 단위`, `표 중심`)로 구성한다. `일반 검색?`의 물음표는 버튼으로 구현하고 tooltip/popover에 원리와 트레이드오프를 적는다.
- 체크 선택은 카드 헤더의 checkbox만으로 한다. 기본 keyboard 순서는 질문 → 후보 checkbox → 인용 → 원본 보기 → 하단 행동이다.
- 동점 시 완료 버튼은 disabled지만 `aria-describedby`로 비활성 이유를 연결한다. 사용자가 선택하지 않고 다음 라운드로 넘어가는 것은 `이번 답변에서는 고르지 않음`으로 기록될 수 있음을 작은 안내문으로 알린다.

### 4.4 상세: 검색과 설정 관리를 섞지 않기

```text
좌측 288px: 문서 (검색 범위)                 중앙: [검색] [설정 스펙]
☑ 출장비_지급_규정.pdf · 조항 단위·일반 검색       검색 탭: 대화와 인용
☑ 복리후생.pdf · 문단 단위·정밀 검색              설정 탭: 읽기 전용 모델/GraphRAG/문서 메타데이터
[+ 문서 추가]
```

- 좌측 문서 목록은 검색 범위 선택 전용이다. 설정 변경·삭제 메뉴는 문서 관리 탭/섹션으로 보내 검색 경험을 어지럽히지 않는다.
- 선택 문서의 검색 방식이 다를 때만 `검색 방식` select를 보인다. 기본은 `일반 검색`; 가능한 값은 현재 선택 범위의 문서에서 실제 존재하는 방식뿐이다.
- 검색 민감도는 실사용 검색에서만 보인다. `유연하게 / 평이하게 / 엄격하게` radio group + 도움말을 쓴다.
- 인용 칩 클릭은 EvidencePanel을 열어 해당 문서·위치를 강조한다. 큰 화면에서는 중앙 우측 보조 패널, 중간 폭 이하에서는 overlay drawer를 사용한다.
- 문서 추가 시에는 full-page 흐름으로 `기존 방식 적용`과 `이 문서 따로 비교`를 먼저 선택한다. 별도 튜닝을 모달로 축소하지 않는다.

## 6. 상태·예외 설계

모든 페이지는 loading, empty, error, forbidden을 구현한다. API가 준비되기 전에는 동일한 상태를 mock fixture로 검증한다.

| 상황 | 화면 처리 | 다음 행동 |
|---|---|---|
| 첫 RAG 없음 | 문서 일러스트 대신 간결한 안내 + 3단계 설명 | `첫 RAG 만들기` |
| 문서 없음 | 검색 composer를 비활성화하고 이유를 표기 | `문서 추가` |
| 파싱/인덱싱 진행 | 단계 progress, 완료 수, 마지막 갱신 시각 | `대시보드로 돌아가기` |
| 일부 후보 실패 | 성공 후보는 비교 가능, 실패 카드는 이유/재시도 표시 | `후보 다시 준비하기` |
| API/네트워크 오류 | 기존 입력과 완료 결과를 보존, 자동 재시도 여부 표시 | `다시 시도` |
| SSE 연결 끊김 | 마지막 생성 위치를 유지하고 `답변 연결이 끊겼어요` 표시 | `이어 받기` 또는 `다시 질문` |
| 근거 부족 | danger가 아닌 경고 표면; 답변 없음 상태로 명확히 표시 | 검색 범위/질문 변경 |
| 권한 없음 | 작업 내용·문서명 노출 최소화 | `접근 권한 요청 방법 보기` |
| 재튜닝 필요 | 대시보드에서 비차단 notice | `비교 다시 시작` |
| 확정 전 이탈 후 복귀 | 원본 문서는 남고, 임시 비교는 다시 준비해야 함을 설명 | `비교 다시 시작` |

## 7. 접근성 및 반응형

### 접근성 완료 기준

- 본문과 표면의 텍스트 contrast는 최소 4.5:1, 큰 텍스트는 최소 3:1을 지킨다. 상태 색상을 단독 의미로 쓰지 않는다.
- 모든 버튼, checkbox, select, citation chip은 키보드로 조작 가능하고 눈에 보이는 focus ring을 가진다.
- tooltip 내용은 hover뿐 아니라 focus에서도 열리고, 핵심 설명은 화면 내 도움말로도 이용 가능하다.
- 스트리밍 답변 영역은 `aria-live="polite"`를 사용하되 토큰마다 전체 답변을 반복 낭독하지 않는다. 상태 변경은 요약 문장만 알린다.
- Step progress는 `현재 단계: 후보 2개 중 1개 준비 완료`처럼 텍스트 대체를 제공한다.
- checkbox에는 후보명, 현재 선택 횟수, 준비 상태가 함께 읽히는 accessible name을 제공한다.
- 인용을 연 EvidencePanel은 focus를 이동시키며, 닫을 때 원래 인용 칩으로 되돌린다.
- `prefers-reduced-motion`에서는 skeleton shimmer, 회전, 카드 진입 애니메이션을 제거한다.

### 반응형 기준

제품은 **데스크톱 우선**이지만 브라우저 폭이 줄어도 작업이 불가능해져서는 안 된다.

| 폭 | 레이아웃 |
|---|---|
| 1440px 이상 | 대시보드 3열, 상세 좌측 문서 패널 + 중앙 작업 영역 + 선택적 근거 패널 |
| 1024–1439px | 대시보드 2열, 비교 카드 2–3열, 근거 패널은 drawer |
| 768–1023px | 상세 좌측 문서 목록은 접히는 drawer, 비교 카드 2열 |
| 767px 이하 | MVP의 주 대상은 아니지만 1열/세로 흐름을 보장. 카드와 CTA는 가로 스크롤 없이 사용 가능해야 한다 |

터치 가능 요소의 최소 크기는 44px(`--rp-touch-target`)이다. 작은 인용 칩은 텍스트 내에서 예외가 될 수 있으나, 키보드 포커스와 충분한 padding을 제공한다.

## 8. 프론트엔드·백엔드 핸드오프

### 필요한 UI 데이터

프론트는 API가 완성되기 전 아래 계약을 mock으로 먼저 고정한다.

```ts
type RagInstanceStatus =
  | 'SETTING_UP' | 'PARSING' | 'CHUNKING' | 'INDEXING' | 'TUNING' | 'READY' | 'FAILED';

type RagProcessingProgress = {
  currentStep: 'PARSING' | 'CANDIDATES' | 'CHUNKING' | 'INDEXING';
  completed: number;
  total: number;
  message?: string;       // 사용자 노출 가능한 지연/재시도 이유
  updatedAt: string;
};

type PipelineCandidate = {
  id: string;
  displayName: string;    // "조항 단위 · 일반 검색"
  technicalDescription: string; // tooltip/popup 전용
  voteCount: number;
  status: 'PREPARING' | 'READY' | 'FAILED';
  failureReason?: string;
};

type Citation = {
  id: string;
  label: string;          // "1" 또는 "제5조"
  sourceId: string;
  sourceName: string;
  segmentId: string;
  excerpt: string;
  locationLabel?: string; // "5쪽 · 제5조"
};
```

- `displayName`은 서버가 주거나 프론트 공통 매퍼가 하나의 기준에서 생성한다. 각 페이지가 검색 방식을 제각각 번역하지 않는다.
- 진행 상태의 `message`은 원인 중심의 사용자용 문구로 제공하고, 디버그 오류 문자열은 로그/세부 정보에 분리한다.
- 답변에는 `hasSufficientEvidence`, `citations`, `elapsedMs`, `streamStatus`가 필요하다. citation 없는 확신형 답변을 정상 상태처럼 렌더링하지 않는다.
- 확정 API 응답은 확정 후보, 삭제될 임시 후보 수, 완료된 문서 메타데이터를 반환해 확인 화면과 결과 toast가 같은 사실을 말하게 한다.

### QA 수용 기준

- 대시보드에서 상태·진행수·재개 행동을 10초 내 확인할 수 있다.
- 업로드 직후 사용자가 화면을 떠나도 processing 상태가 유지되고 재방문 시 최신 상태가 보인다.
- 준비된 후보는 나머지가 처리 중이어도 비교할 수 있으며, 후보 실패가 성공 후보 사용을 막지 않는다.
- 비교 카드는 답변, 인라인 인용, 원본 조각 보기, 소요 시간, 선택 횟수를 모두 제공한다.
- 동점 상태에서 완료 CTA는 작동하지 않고 이유가 읽힌다. 단독 1위여도 최종 확인을 거쳐야 확정된다.
- 실사용 검색과 튜닝 비교는 header badge/copy와 controls가 명확히 달라 오인되지 않는다.
- 근거 부족, loading, empty, error, forbidden, partial failure가 각각 재현 가능하다.
- keyboard-only 및 reduced-motion 환경에서 대시보드·비교·인용·확정 흐름을 끝까지 완료할 수 있다.

## 9. 구현 순서

1. 토큰을 styled-components theme에 매핑하고 `RagStatusBadge`, `AsyncStatePanel`, buttons/focus 스타일을 만든다.
2. Dashboard 카드와 processing mock polling 상태를 만든다.
3. 생성의 questionnaire/upload/step progress를 만든다.
4. `PipelineCandidateCard`, answer streaming shell, citation/evidence interaction을 만든다.
5. 확정 dialog와 상세 검색 workspace를 만든다.
6. 문서 추가·재튜닝, 피드백, 재튜닝 권장 상태를 연결한다.

새 라이브러리는 필요하지 않다. 아이콘은 기존 프로젝트 아이콘 세트가 있으면 그것을 쓰고, 없으면 하나의 접근성 지원 세트를 선택해 공통 어댑터로 감싼다. 외부 비트맵·브랜드 자산은 MVP에 필요하지 않으며, 문서의 명료함을 우선한다.
