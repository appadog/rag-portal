# Sprint 02 — 후보별 실제 청킹과 검증 가능한 비교

## Objective

튜닝 화면의 후보가 단지 라벨만 다른 상태를 끝내고, 각 청킹 전략이 실제로 다른 근거 조각을 만들어 검색·인용·재방문 복원까지 일관되게 수행하게 한다.

## Delivered

- 후보마다 파생 청크를 생성하고 저장했다.
  - `document`: 문서 전체
  - `semantic`: 파싱된 인접 단위를 읽기 좋은 크기로 묶음
  - `hierarchical`: 조/장/heading 경계를 보존
  - `fixed`: 겹침을 둔 고정 길이 청크
  - `table`: 헤더를 보존한 행 묶음
- 비교 라운드와 확정 뒤 검색이 해당 후보의 청크만 대상으로 검색한다.
- 인용 URL은 원시 파싱 조각과 후보 파생 조각 모두 원문 위치로 열 수 있다.
- 후보의 실제 준비 조각 수를 비교 카드에 표시한다.
- 기존 SQLite snapshot에 후보 청크가 없을 때 원문에서 안전하게 재생성해, 이전 로컬 데이터도 계속 열 수 있다.

## Acceptance checks

- 구조화 문서에서 의미 중심과 구조 중심 후보의 청크 경계·개수가 달라진다.
- 비교 답변의 citation은 해당 후보가 만든 청크를 가리킨다.
- 확정 후 검색과 근거 뷰어가 파생 청크를 사용한다.
- 프로세스 상태 복원 뒤에도 후보 청크와 비교 결과를 다시 확인할 수 있다.

## Deliberate boundary

이번 스프린트의 검색은 결정론적 로컬 lexical retrieval이다. 외부 임베딩 모델 호출과 벡터 검색은 `HF_TOKEN`, 비용·재시도 정책, 벤치마크 코퍼스·정답 라벨에 대한 제품 결정을 먼저 확정한 뒤 다음 단계에서 연결한다.
