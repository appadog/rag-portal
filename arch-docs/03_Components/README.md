# Enterprise RAG 컴포넌트 상세 설계 작성 기준

## 1. 목적

본 문서는 [Component Architecture](../02_Component_Architecture.md)에서 정의한 소프트웨어 컴포넌트를 동일한 깊이와 형식으로 상세 설계하기 위한 공통 기준이다.

컴포넌트 상세 설계는 다음 질문에 답한다.

- 컴포넌트 내부 책임을 어떤 모듈로 구분하는가?
- 각 모듈이 소유하는 판단과 상태는 무엇인가?
- 컴포넌트가 수용하고 제공하는 의미적 Operation은 무엇인가?
- 정상·실패·재처리 흐름과 상태 생명주기는 어떻게 구성되는가?
- Tenant 격리, 지식 근거, 추적성과 관찰성 제약을 어떻게 적용하는가?
- 후속 API·데이터·물리 설계에 어떤 명세와 결정을 전달하는가?

상세 설계의 내부 모듈은 구현 책임을 설명하기 위한 단위이며, 클래스·패키지·프로세스 또는 독립 배포 단위와 반드시 일치하지 않는다.

## 3. 공통 설계 수준

### 3.1 포함 범위

- 컴포넌트 내부 모듈과 책임
- 내부 의존 방향
- 입력·출력과 의미적 Operation
- 핵심 정보의 의미와 논리 필드
- 상태, 생명주기와 전이 조건
- 주요 정상·실패·재처리 흐름
- 오류 분류와 복구 원칙
- 동시성, 멱등성과 업무 일관성 경계
- Tenant, 보안과 민감정보 제약
- OpenTelemetry 기반 관찰정보
- 설정 범주와 구현 교체 경계
- 상위 설계 추적과 구현 수용 시나리오

### 3.2 제외 범위

- HTTP 경로, Method와 응답 코드
- JSON Schema와 이벤트 Schema
- DB 테이블, 컬럼, 인덱스와 물리 저장소
- Framework, 라이브러리와 제품 선정
- 서비스 수, 컨테이너와 네트워크 구성
- Queue, Broker와 통신 프로토콜 선정
- 세부 검색·Chunking·Reranking·Grounding 알고리즘
- OpenTelemetry Collector와 Backend 토폴로지

제외 범위가 상세 설계 판단에 필요하면 확정하지 않고 `미결정 사항`으로 기록한다.

## 4. 공통 문서 구조

각 컴포넌트 문서는 다음 구조를 사용한다.

1. 목적과 범위
2. 책임과 경계
3. 내부 구성
4. 핵심 정보 모델
5. 상태와 생명주기
6. 주요 처리 흐름
7. 컴포넌트 Operation 명세
8. 오류와 복구
9. 동시성, 멱등성과 일관성
10. Tenant, 보안과 권한
11. 관찰성과 운영정보
12. 설정과 확장 지점
13. 제약과 미결정 사항
14. 상위 설계 추적
15. 구현 수용 시나리오
16. 상세 설계 완료 점검

상태가 없는 컴포넌트는 상태를 억지로 만들지 않고 화면 또는 실행 상태처럼 해당 책임에 맞는 생명주기를 정의한다.

## 5. 공통 컨텍스트

Backend 컴포넌트는 요청 목적에 따라 필요한 공통 컨텍스트를 수용한다.

| 컨텍스트 | 의미 | 공통 제약 |
|---|---|---|
| Tenant Context | Tenant 업무 데이터와 실행의 최상위 격리 범위 | 누락되거나 대상과 불일치하면 처리하지 않는다. 시스템 공통 자원 관리정보에는 적용하지 않는다. |
| Subject Context | 외부에서 검증된 사용자 또는 호출 주체 참조 | 대화 소유권과 감사에 사용하며 사용자별 Knowledge Base 권한으로 확장하지 않는다. |
| Request Context | 업무 요청과 멱등성을 식별하는 맥락 | 관찰용 Trace Context와 구분한다. |
| Knowledge Scope | Tenant 안에서 요청된 Knowledge Base와 지식 범위 | 하위 처리에서 임의로 확장하지 않는다. |
| 외부 자원 구성정보 | Resource Manager가 관리하는 역할별 외부 자원의 참조, 적용 관계와 호환성 기준 | 실행 컴포넌트가 임의로 변경하거나 Tenant별로 재정의하지 않는다. |
| Trace Context | 분산 실행을 연결하는 OpenTelemetry/W3C 맥락 | 외부 자원 호출까지 연속성을 유지한다. |
| Evaluation Context | 운영 실행과 평가 실행을 구분하는 맥락 | 평가 실행에만 적용하고 운영 이력을 오염시키지 않는다. |
| Strategy Selection Context | 운영 실행과 초기 전략 비교 실행을 구분하는 맥락 | 지정된 Tenant·Knowledge Base·후보 범위를 벗어나거나 운영 지식과 혼합하지 않는다. |

구체적인 필드, Header와 신뢰 검증 방식은 API 및 보안 설계에서 정의한다.

## 6. Operation 작성 기준

Operation은 구체적인 Endpoint가 아니라 컴포넌트가 제공하거나 요구하는 의미적 상호작용 명세이다.

각 Operation은 다음을 정의한다.

- 목적
- 요청 주체
- 필수 입력
- 성공 결과
- 주요 거부 조건
- 상태 변경 여부
- 멱등성 요구

Operation 이름은 구현 프로토콜과 무관한 동사형 영문 이름을 사용한다.

```text
SubmitQuestion
PublishKnowledge
StartEvaluation
SubmitFeedback
```

API 설계에서는 Operation을 외부 또는 내부 API와 이벤트로 매핑한다.

## 7. 상태와 일관성 기준

- 상태 변경은 해당 정보의 소유 컴포넌트만 수행한다.
- 상태 전이는 명시적인 허용 조건을 통과해야 한다.
- 다른 컴포넌트의 성공을 로컬 상태로 추정하지 않는다.
- 외부 자원 호출과 로컬 상태 변경은 하나의 분산 트랜잭션으로 가정하지 않는다.
- 부분 성공은 숨기지 않고 재처리 가능한 상태와 원인을 유지한다.
- 동일 멱등성 범위의 중복 요청은 같은 업무 결과를 재사용하거나 명시적으로 충돌 처리한다.
- Tenant가 다른 요청과 정보는 같은 일관성 경계에 포함하지 않는다.

---

## 8. 외부 자원 인터페이스 기준

External Resource Interface는 각 Backend 내부의 외부 접점 책임으로 배치한다.

공통 원칙은 다음과 같다.

- Resource Manager가 관리하는 시스템 공통 외부 자원 구성을 사용한다.
- 외부 제공자별 요청·응답과 오류 차이를 핵심 업무 모듈에서 격리한다.
- Secret 원문을 업무정보와 실행 이력에 저장하지 않는다.
- 외부 호출 결과와 적용된 외부 자원 구성정보를 추적한다.
- 임베딩 생성과 검색에 사용하는 자원의 호환 조건을 확인한다.
- 외부 실패를 무조건 성공이나 빈 결과로 변환하지 않는다.

Resource Manager는 관리 책임을, External Resource Interface는 실행 시 외부 자원과 상호작용하는 책임을 가진다.

외부 자원 구성 이력은 실행 결과와 호환성에 영향을 주는 변경, 구성의 적용·적용 종료·복원 관계와 업무 결과에 실제 적용된 구성정보를 추적하는 범위로 제한한다. Secret 변경은 외부 Secret 관리 체계가, 일시적인 가용성과 오류는 관찰 체계가 책임진다. 설명·표시정보처럼 실행 결과와 호환성에 영향을 주지 않는 변경은 필수 이력 대상이 아니다.

외부 자원 구성정보의 불일치를 외부에서 자동 탐지하거나 구성을 자동 비활성화하는 기능은 공통 책임에 포함하지 않는다.

## 9. 관찰성과 민감정보 기준

각 Backend는 OpenTelemetry 기반 Trace, Metric과 구조화 Log를 제공할 수 있어야 한다.

공통 관찰 대상은 다음과 같다.

- 업무 Operation과 상태 전이
- 내부 주요 처리 구간
- 컴포넌트 간 요청
- 외부 자원 호출
- 처리 시간, 성공·실패와 재처리
- Tenant 범위를 직접 노출하지 않는 안전한 구분정보

다음 정보는 관찰정보에 기본적으로 포함하지 않는다.

- 원본 문서 내용
- Knowledge Unit 원문
- 사용자 질문과 생성 답변 원문
- 프롬프트 원문
- 인증 Token, Secret과 연결정보 원문

필요한 업무 식별자는 별도 마스킹·해시·접근통제 정책을 거쳐 사용한다.

---

## 10. 문서 간 일관성 기준

- Concept의 목적과 원칙을 변경하지 않는다.
- Logical Architecture의 책임 영역을 누락하지 않는다.
- Component Architecture의 책임 소유권과 의존 방향을 유지한다.
- 동일한 정보와 상태는 하나의 컴포넌트만 소유한다.
- Operation 요청·응답의 의미를 양쪽 컴포넌트 문서에서 일치시킨다.
- 정보 흐름과 정적 의존 방향을 구분한다.
- 미결정 사항을 암묵적인 구현 결정으로 대체하지 않는다.

후속 과제와 작업 이력은 [WORK_STATUS](../../WORK_STATUS.md)에서 관리한다.
